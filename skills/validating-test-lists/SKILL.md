# Validating Test Lists

## 개요

**테스트 목록은 피처 정의를 기준으로 검증한다.** 피처가 요구하는 동작·business rule·state transition·경계·invariant 에서 "기대 동작 목록(expected-behavior inventory)"을 도출하고, 사용자가 제안한 각 테스트를 거기에 비춰 판정한다. 모든 판정에는 **근거**가 붙는다 — 어떤 피처 규칙에서 나왔는지, 또는 어떤 기존 테스트와 겹치는지.

기준은 피처지만, **연관된 기존 코드·테스트를 보조로 확인**한다: (a) 이미 커버된 중복을 걸러내고, (b) 피처가 건드리는 기존 제약/invariant 에서 놓친 경계를 찾고, (c) 실현 가능성을 점검한다. 주(主)는 피처 정의, 코드는 보조.

이건 *이미 작성된 테스트 코드 감사*가 아니다 (그건 별도 테스트 감사 도구의 몫 — 예: test-reviewer 류 리뷰 에이전트). 구현이 아직 없을 수도 있다 (새 피처 / TDD) — 그래서 기준은 "구현 코드"가 아니라 "피처 정의"다.

## 사용 시점

- 새 피처를 정의하고 테스트 코드를 짜기 **직전**, 케이스 목록이 충분한지 검증
- 사용자가 테스트 목록을 주며 "충분한가? / 빠진 거 없나? / 이 테스트 필요한가?" 물을 때
- TDD fail-first 전, spec 작성 전 케이스 목록 검증

**쓰지 않을 때:**
- 이미 작성된 테스트 감사 → 별도 테스트 감사 도구 (예: test-reviewer 류 에이전트. 없으면 코드 리뷰 단계에서)
- 테스트 코드 작성 자체 → 테스트 작성 도구/에이전트 (예: test-writer 류. 없으면 직접 작성)
- 피처 정의가 없음 → 검증할 기준이 없으니 정의부터 확정한다

## 철칙

**피처 정의 없이는 판정 없음. 근거 없이는 판정 없음.** 피처가 모호하면 그것부터 드러낸다 — 정의되지 않은 피처에는 테스트를 검증할 수 없다. 모든 KEEP/MODIFY/DELETE/ADD 에는 피처 규칙 또는 기존 spec 근거가 따라붙는다.

## 절차

### 0. 대상 확정 (시작 게이트)
**피처 정의(요구사항 문서)** 가 지정되지 않았으면 코드·문서 탐색으로 추정하지 말고 한 줄 질문으로 확정한 뒤 시작한다. **테스트 리스트는 다르다 — 지정되지 않았으면 출처를 묻지 말고 아래 핑퐁(학습) 모드가 기본이다** (리스트 부재는 오류가 아니라 입구). 리스트가 지정됐으면(plan 목록 검증 등) 표준 판정으로 진행하되, 사용자가 "핑퐁으로"를 명시하면 그 리스트를 P4 합류분으로 미루고 핑퐁 모드로 돈다. 같은 피처 정의에 대한 재실행이면 전체를 재판정하지 않는다 — 직전 판정 이후 **변경분(추가·수정된 케이스)만** 판정한다 (전체 재검증은 사용자가 명시할 때만).

### 1. 피처 정의를 확정하고 기대 동작을 도출
피처 정의에서 다음을 뽑아 **expected-behavior inventory** 를 만든다:

- 핵심 동작과 **business rule**
- **state transition** (예: `review → approved`) 과 전이 조건
- **경계값** (개수 임계, 금액, 시간, 비율)
- **에러 조건 / 거부 경로** (권한, 중복, 부족, 충돌)
- **invariant** (항상 참이어야 하는 것)
- **재화 / 원자성 / 멱등성** 요구 (차감-실패 시 rollback 등)
- **필수 통합 체인** — 여러 동작을 잇는 생산자→소비자 흐름 중 *반드시 끝까지 동작해야 하는* 것 (예: 큐 재진입 → 배정 → 완료 → 다음 진입). 반복 가능한 액션이면 반복 시 불변식(예: 활성 엔트리 ≤ 1)도 함께 도출한다.

정의가 모호하면 임의로 채우지 말고 질문한다 (예: "비용이 2~3 포인트 — 정확히 몇? 범위로는 단언을 못 박는다").

### 2. 연관 기존 코드·테스트를 보조로 확인
Glob/Grep 으로 (범위 넓으면 Explore 에이전트 dispatch):

- 연관 `*.spec.ts` — **이미 커버된 것**은 다시 제안하지 않는다 (중복 근거로 쓴다)
- 연관 모델/서비스 — 이 피처가 **건드리는 기존 제약/invariant** → 놓친 케이스 또는 도달 불가능 판단
- 기존 패턴 — 같은 종류의 동작이 이미 테스트되는 방식

### 3. 각 제안 테스트를 분류 (근거 필수)
항목마다 판정 하나 + 근거(피처 규칙 또는 기존 spec):

| 판정 | 의미 |
|---|---|
| **KEEP** | 피처의 실제 규칙/동작에 매핑됨; 단언 대상이 옳음 |
| **MODIFY** | 규칙은 맞으나 단언이 약함/틀림 — 경계가 너무 좁거나, 관찰 불가능한 것을 단언 (5번 참조) |
| **DELETE** | 불필요 — 기존 테스트와 중복, 또는 피처 범위 밖, 또는 framework/library 보장을 테스트, 또는 어떤 피처 규칙과도 무관 |
| **CLARIFY** | 피처 정의가 모호해 이 테스트의 옳고 그름을 아직 판정 불가 → 결정해야 할 질문으로 올린다 |

### 4. 빠진 항목 도출 (ADD)
expected-behavior inventory 를 훑어 **제안 테스트가 없는** 동작·경계·에러 경로·invariant 를 ADD 후보로 올린다. 각각 어떤 피처 규칙에서 나왔는지 근거를 단다. **필수 통합 체인**(시작점만 만들고 종착점까지 실제 호출 / 반복 N≥2 불변식 / 트랜잭션 가드는 real txn) → **재화/원자성·state-count 경계·중복/권한 가드** 순으로 우선한다 — 사용자가 스펙만 보고 가장 자주 놓치는 곳이다.

필수 통합 체인은 단일 케이스가 아니라 *흐름*이라 inventory 에서 가장 자주 누락된다. 체인마다 다음 3축을 점검한다:
- **종착점**: 중간 성공 지점(예: 배정 성사)이 아니라 흐름의 종착점(완료 → 정리 → 다음 진입)까지 실제 호출로 도는 통합 케이스가 있나. 중간 상태를 손으로 seed 하지 않는다 (그래야 생산자 측 이음새 버그가 잡힌다).
- **반복**: 반복 가능한 액션이면 N≥2회 시나리오가 있나. 단언은 *횟수 결과*(`count==1`)가 아니라 **불변식**(중복 누적 없음·유일성 등)인가 — 1회만 돌리면 누적 버그가 형성되지 않아 공허하다.
- **트랜잭션**: 가드/정리가 트랜잭션 안이면 실제 트랜잭션이 동작하는 환경을 요구하나 — 트랜잭션을 흉내만 내는 테스트 더블은 abort/rollback 버그를 재현 못 한다.

### 5. behavior-contract 패스
단언 대상이 관찰 가능한 최종 state 가 아닌 테스트는 거부하고 재작성한다:
- "X 함수가 호출됐다 / mock called" → 결과 **state** 를 단언 (잔액, status, 큐 내용)
- "예외가 전파된다 / error propagates" → 관찰 가능한 결과를 단언 (요청 거부됨, state 불변)
- "호출 순서가 맞다 / call order" → 순서가 아니라 최종 state 를 단언

### 6. 리포트
- **판정 표**: 항목 → 판정 → 근거(피처 규칙 / 기존 spec)
- **ADD 목록**: 빠진 케이스, 피처 근거와 함께, 우선순위순
- **명세 모호점**: 테스트 설계를 막는 결정 사항 — 임의로 채우지 말고 질문

## 핑퐁(학습) 모드 — 리스트 미지정 시 기본

목적은 판정만이 아니라 **테스트 설계 감각의 체화**다. 답을 먼저 본 상태에선 "안다" 착각이 생겨 학습이 일어나지 않으므로, 먼저 묻고 나중에 보탠다 (suite `PRINCIPLES.md` §1 피드백 모드·§3 학습 모드의 no-pre-fill 과 같은 규율 — 이 스킬은 페르소나 스킬이 아니라 원칙 로드는 없지만 규율은 동형). 새 판정 메커니즘은 없다 — **기존 절차 1~6의 순서 재배열**이다.

**opt-in 이 아니라 기본인 이유**: 호출 키워드에 의존하면 부르는 걸 잊는 순간 영영 안 돈다 — offer·키워드 의존이 조용히 누락되는 실패는 이미 실측된 부류다(DESIGN §7 스케일 라운드 "실행자 누락"). 대신 **강등을 열어둔다**: P2 되묻기에 사용자가 "그냥 판정만 해 / plan 목록으로 해"라고 답하면 표준 판정으로 내려간다 — P1 의 inventory 는 그대로 판정 기준으로 재사용되므로 선고정 비용은 낭비되지 않는다. (2회 연속 강등이면 기본을 opt-in 으로 되돌린다 — DESIGN 거취 트리거 보드.)

P1. **inventory 선고정 (비공개)**: 절차 1(+절차 2 보조 확인)을 먼저 수행하되 **대화에 출력하지 않는다** — 임시 파일(세션 스크래치 등)로 저장해 고정한다. 이게 "검증자의 독립 리스트"다.
   - **고정 후 수정 금지.** 사용자 답을 본 뒤 inventory 를 고치면 두 리스트가 독립이 아니게 돼 대조의 진단 가치가 죽는다 (앵커링 — §10 결정 반박이 fresh context 를 쓰는 것과 같은 이유의 *시간* 버전). 사용자 답에서 배운 것은 P4 의 "사용자가 잡고 inventory 가 놓친 것" 칸으로 간다.
P2. **되묻기**: "이 피처에 어떤 테스트를 짤 건지 리스트업해봐." inventory 의 내용은 물론 **개수·카테고리 힌트도 싣지 않는다** (개수만 알려줘도 사용자는 그 수에 맞춰 짜낸다). 막혔을 때만 2~3개 각도 제시 — 항목을 대신 채우지 않는다.
P3. **사용자 리스트 판정**: 절차 3·5 그대로 — KEEP/MODIFY/DELETE/CLARIFY + 근거, behavior-contract 패스. 이 단계까지 inventory 는 여전히 비공개이며, 판정 근거는 피처 규칙 인용이다 — "내 리스트에 없어서"는 근거가 아니다.
P4. **공개 대조 (양방향 diff)**: 고정해둔 inventory 를 공개하고 대조한다.
   - 사용자가 놓친 것 → ADD (절차 4 우선순위 그대로: 필수 통합 체인 → 재화/원자성 → 경계·중복·권한)
   - **사용자가 잡고 inventory 가 놓친 것도 명시** — diff 는 채점이 아니라 상호 대조다.
   - 놓친 항목마다 **유형 태그** 한 토큰(경계/체인/불변식/트랜잭션/멱등/에러경로).
   - **태그 착지 (한 줄 append)**: `<repo>/.claude/test-design-log.md` 에 `- [YYYY-MM-DD] <피처> | 사용자 놓침: <태그들> | inventory 놓침: <태그들>` 을 append 한다 (파일 없으면 생성). "같은 태그 반복 = 약점 신호"는 세션이 서로를 못 보므로 이 로그 없이는 판정 불가다 — 관측 데이터가 구조적으로 안 남는 지점(역주입 큐·스케일 라운드 기록 의무와 같은 부류). 대조 시 이전 로그를 먼저 읽어 반복 태그면 **"N회째"** 로 명시한다 — 반복 약점이 곧 다음 학습 포인트다. (로그를 P2 되묻기 전에 읽는 건 무방 — 사용자의 과거 약점이지 이번 inventory 힌트가 아니다.)
P5. **병합**: 최종 리스트 확정(결정은 사용자) → plan/스펙 반영 (절차 6 리포트 형식).

**plan 순서 함정**: 구현 계획(6a) 산출물에는 보통 테스트 목록이 이미 있다 — 사용자가 그걸 읽은 뒤면 P2 는 pre-fill 된 상태라 학습이 죽는다. 핑퐁 모드는 **plan 의 테스트 섹션을 열기 전**(또는 6a 전, 피처 문서 기준)에 돌리고, plan 의 목록은 P4 에서 3-way 로 합류시킨다.

**한계 + escalate (선택)**: 같은 모델이라 prior 는 공유된다 — 사용자와 inventory 가 같은 맹점이면 diff 에 안 잡힌다 (하류 oracle 인 TDD 실행·8.5 감사가 2차). 무거움 tier(재화·동시성·마이그레이션)면 P1 을 fresh-context read-only 서브에이전트로 독립 생성하는 escalate 옵션 — 기본은 시간적 선고정으로 충분 (right-size).

## Quick Reference

```
피처 정의            →  expected-behavior inventory (동작·전이·경계·에러·invariant·재화)
연관 코드/테스트(보조) →  이미 커버된 것(중복) + 건드리는 기존 제약
각 제안 테스트        →  KEEP / MODIFY / DELETE / CLARIFY  (+ 피처 규칙·spec 근거)
빠진 동작·경계        →  ADD (필수 통합 체인[종착점·반복·txn] → 재화/원자성·count 경계·중복/권한 순)
관찰 불가능한 단언     →  최종 state 로 재작성
모호한 명세          →  플래그 & 질문, 임의로 채우지 않음
핑퐁(학습) 모드       →  [리스트 미지정 시 기본] inventory 선고정(비공개·수정 금지) → 되묻기(힌트 0 · "그냥 판정만"이면 표준 강등) → 판정 → 공개 대조(양방향 diff + 유형 태그) → 병합
```

## 흔한 실수

- **피처 정의 없이 목록부터 판정한다.** 검증할 기준이 없으니 일반론만 나온다. 정의(또는 모호점)부터 확정한다.
- **근거 없이 판정한다.** "이것도 추가하면 좋음" 식 제안 금지 — 어떤 피처 규칙/기존 spec 때문인지 반드시 댄다.
- **연관 기존 테스트를 안 보고 중복을 제안한다.** 기준은 피처지만, 이미 있는 테스트는 코드로 확인해야 걸러진다.
- **피처 범위 밖 테스트를 받아준다.** 피처가 정의하지 않은 동작은 KEEP 이 아니라 DELETE 또는 CLARIFY.
- **"X 호출됨" 식 테스트를 받아준다.** mock-call / exception-propagation / call-order 단언은 behavior contract 위반 — 관찰 가능한 state 로 재작성.
- **모호한 명세를 직접 채운다.** "2~3 포인트"나 "approved (rejected 는?)" 는 사용자가 내릴 결정 — 질문으로 드러낸다.
- **(핑퐁 모드) 되묻기 전에 힌트를 흘리거나, 사용자 답을 본 뒤 inventory 를 고친다.** 내용은 물론 개수·카테고리 힌트도 pre-fill 이고, 사후 수정은 두 리스트의 독립성을 깨 diff 의 진단 가치를 죽인다 — inventory 는 파일로 선고정, 공개는 판정 후.
- **케이스는 다 봤는데 체인을 안 본다.** 단일 케이스를 잘 판정해도, 여러 케이스를 잇는 필수 흐름(생산자→소비자 + 반복)이 리스트에 없으면 그 이음새 버그가 통째로 빠진다 — 종착점까지 도는 통합 케이스 1개를 ADD. 특히 반복 가능한 액션을 1회만 검증하거나, 트랜잭션 가드를 트랜잭션 없는 환경으로 검증하는 케이스를 경계한다.
